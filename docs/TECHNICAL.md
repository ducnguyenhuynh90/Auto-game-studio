# Technical

- Vite 6 + TypeScript 5.8 (strict), three.js 0.170, Vitest 3. Production bundle ≈ 160 KB gzipped.
- Two stacked canvases: `#world` (WebGL) under `#game` (2D UI). Both are sized to the 390×844 logical view,
  scaled to fit the window at devicePixelRatio ≤ 3.
- Input: Pointer Events → `Game.pointerDown/Up`. Immediate-mode hit areas are rebuilt each frame, and only
  the top overlay is interactive.
- Persistence: localStorage `mam_save_v1` (versioned). Analytics: see docs/ANALYTICS.md.
- Audio: procedural WebAudio SFX (no assets), unlocked on first tap. Haptics through `navigator.vibrate`.
- Deploy: `.github/workflows/pages.yml` builds and publishes `dist/` on pushes to `main`
  (Pages must be enabled in the repo settings). CI runs tests and build on branches and PRs.
- Known: `npm audit` flags dev-only vitest deps (tinypool/@vitest/mocker); there is no runtime exposure.

## Performance on weak devices (build 2.2)
- **Quality tiers** (`src/render3d/quality.ts`): high / medium / low control max DPR, render scale, antialias,
  shadow map, ink outlines (they double draw calls), water tessellation, a 30 fps cap for the 3D layer,
  and particle counts. The 2D UI canvas is capped at 2× DPR (1.5× on low).
- **Pick:** Settings choice → else the remembered auto result → else device hints (cores, memory, mobile).
- **FpsGovernor:** in auto mode, judges every ~2 s of play and steps high→medium→low under 40 fps.
  It only steps down within a session and remembers the result for the next visit.
- **Savings independent of tier:** no per-frame normal recompute on flat-shaded water; fish models are
  built once per species and cloned (shared geometry); the WebGL layer stops rendering under full-screen
  menus (`covers3d`); removed models free their one-off geometry.
- **Benchmark:** `node tools/bench.mjs <cpuSlowdown> [quality]` (dev server; headless software GL at DPR 2
  is a harsh proxy for a weak phone). Results below.

## Caching / offline
- Vite splits three.js into its own content-hashed chunk, so game updates don't re-download it.
- `src/sw/sw-template.js` → `dist/sw.js` (generated by a small Vite plugin with the exact precache list and
  a build-hash version). Hashed assets are cache-first; pages are network-first with an offline fallback.
  Lookups use `ignoreVary` (servers sending `Vary: Origin` otherwise miss module scripts).
- Installable PWA: `public/manifest.webmanifest` + icons. The service worker only registers on
  self-hosted production builds (not in dev, not inside the claude.ai artifact frame).

## Accounts & cloud save
- Guest play is the default. `src/auth/account.ts` adds cloud backup when signed in:
  - **claude.ai account** (playtest artifact): automatic; save at `data/users/<viewer id>/save`, private
    per player. Needs the player to have Contributor access or be in the org (same as analytics).
  - **Google / Apple / Facebook** via Firebase (`src/auth/firebase.ts`): compiled in only when
    `VITE_FIREBASE_*` is set (build-time `__FIREBASE__`), lazy-loaded (≈109 KB gz) only for returning
    social players or when Settings opens. Save at Firestore `saves/{uid}`; rules in `firestore.rules`.
- **Merge** (`src/auth/merge.ts`, tested): no cloud → upload; a fresh side yields to the other; same
  `saveId` → higher `rev` wins; two different journeys → the player chooses in Settings.
- **Data minimisation:** we store the save and a first name only. No email is requested.

### Supabase: player accounts + progress (build 3.6, recommended backend)
- `src/auth/supabase.ts`, compiled in when `VITE_SUPABASE_URL` + `VITE_SUPABASE_ANON_KEY` are set at build
  time (`__SUPABASE__`; Firebase is then ignored). Lazy-loaded chunk ≈ 60 KB gz; guest builds unchanged.
- **Every player is backed up from the first launch:** an anonymous Supabase user is created silently.
  Settings shows "Guest · backed up to the cloud" with **Link Google / Apple / Facebook**: linking keeps
  the same user id (`linkIdentity`), so the save follows the player to any device. If that social account
  already exists, it signs in to it instead and the normal merge rules decide (or ask).
- **Tables** (`supabase/migrations/20261025000000_players.sql`):
  - `profiles`: `id` (= auth user), `display_name` (first name or "Guest"), `provider`, `created_at`, `last_seen`.
  - `saves`: `user_id`, `state` (the whole GameState as jsonb, ≤ 500 KB), `save_id`, `rev`, `saved_at`, and a
    progress summary for support/dashboards: `captain_level`, `coins`, `catches`, `sea`, `relics`,
    `island_level`, `brand_level`, `updated_at` (trigger).
  - **Row-level security:** players read/insert/update only their own rows; no delete policy (deleting the
    auth user cascades). Verified in `tests/supabase.test.ts` by running the migration in PGlite (real
    Postgres) as two different users.
- **Sync:** the same AccountManager as before: upload at most every 15 s and when the app goes to the
  background; merge rules in `src/auth/merge.ts`. If Supabase can't be reached the game plays on the
  device and says so in Settings.
- **E2E without a project:** `tools/supabase-e2e.mjs` fakes Supabase at the network level in Chromium:
  anonymous sign-in → profile + save + summary uploaded → local save wiped → cloud save restored;
  and Supabase down → the game still starts. (Build with the fake URL first; see the file header.)
- **Privacy:** our tables hold a first name and the sign-in method, never email. For social logins the
  Supabase auth service itself keeps the email to sign the player in; we never read or use it.

### Founder setup for Supabase (about 20 min, free plan)
1. supabase.com → New project (Free plan; pick a region near players, e.g. Singapore).
2. SQL editor → paste and run `supabase/migrations/20261025000000_players.sql`.
3. Authentication → Sign In / Providers: turn on **Allow anonymous sign-ins**; enable **Google** (Google
   Cloud OAuth client), optionally **Facebook** (Meta app) and **Apple** (Apple Developer, $99/yr: a real
   cost, founder decision). Allow manual linking (Auth settings) so guests can link a login.
4. Authentication → URL Configuration: Site URL = the game URL (e.g. `https://<user>.github.io/Auto-game-studio/`),
   and add it to Redirect URLs.
5. Project Settings → API: copy the Project URL and the anon public key into `.env` locally, and into GitHub
   → Settings → Secrets and variables → Actions as `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`
   (the Pages workflow passes them to the build). The anon key is public by design; RLS protects the data.
6. Optional: Auth → Rate limits / CAPTCHA for anonymous sign-ups if bots appear.

### Founder setup for Firebase social login (older alternative, about 30 min, free tier)
1. console.firebase.google.com → new project (Spark plan, no billing) → add a Web app → copy the config
   into `.env` (see `.env.example`).
2. Authentication → Sign-in method: enable Google. Facebook needs a Meta developer app (App ID/secret).
   Apple needs an Apple Developer account ($99/yr: **a real cost, founder decision**).
3. Authentication → Settings → Authorized domains: add the hosting domain (e.g. `<user>.github.io`).
4. Firestore → create database → paste `firestore.rules` → Publish.
5. Add the same `VITE_FIREBASE_*` values as GitHub Actions secrets/vars so the Pages build includes login.
6. Before public launch: a privacy policy page (stores need one when login exists).

| | before (2.1) | after (2.2, auto→low) |
|---|---|---|
| 6× CPU slowdown: village / fishing / reef fps | 2 / 3 / 3 | 15 / 22 / 23 |
| no slowdown: village / fishing / reef fps | 4 / 4 / 4 | 29 / 49 / 55 |
| load to playable (no slowdown) | ≈2.3 s | 0.5-1.6 s |
| offline reload (built, service worker) | fails | ≈1.3 s |
Software GL is far slower than any real phone GPU; real devices should do better. Real-device numbers are still TODO.
